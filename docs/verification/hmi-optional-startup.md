# Optional HMI module startup qualification

The actual MCP host and V21 worker passed `bridge_info` (`tia_capabilities`), `discover` (`tia_discover`), `hmi_capabilities`, and detached `session_status` with both HMI families absent from the configured API directory. A test-only CLR assembly-load observer saw the actual installed `Siemens.Engineering.Base` and `Siemens.Engineering.Contract` assemblies load, and no `Siemens.Engineering.WinCC`, `Siemens.Engineering.WinCC.Extension`, or `Siemens.Engineering.WinCCUnified` assembly load. No project was opened, attached, started, changed or deployed by this test.

Authoritative absence evidence: `artifacts/hmi-optional-startup-20261008-final-absence/report.json`, `managed-assemblies.tsv`, and `host.log`. The report records exact host/worker hashes, source assembly signatures and hashes, configured paths, all MCP responses, the isolated configuration hash, observer hash and native process evidence. The worker executable SHA-256 is `2fcec6ae477856ec48a6b5b394fe505c120caf18a0e9be55c3721c9ea664d596`; its IL was unchanged. Both family diagnostics reported `installed: false`, `apiAvailability: unavailable`, `HmiPrerequisiteMissing`, `license: notProbed`, and `nativeQualification: unverified`. All four calls, managed assembly observation, and clean host exit passed independently in each of the three final runs below.

## Fidelity and controls

The test copies only the locally installed, signature-verified Base, Step7 and Safety V21 public API DLLs into a new ignored `artifacts/…/api-core-only` directory, retaining their exact hashes. It copies no Siemens HMI assembly and includes no Siemens DLL in the worker output. These local test files are not release-bundle contents.

Siemens' `OpennessLocationProvider` uses the Base assembly's installed location. Simply relocating all three core DLLs made native discovery fail even though `bridge_info` succeeded. To isolate the optional-module question, a test-only `.exe.config` uses .NET Framework `codeBase` entries for exactly Base, Step7 and Safety at their installed signed originals. Optional HMI resolution still uses the filtered API directory. The worker binary remains identical; the configuration difference is retained and hashed. This is an actual configured-module-absence test on a machine which still has WinCC installed, not a claim that WinCC was uninstalled or that a fresh PLC-only machine was qualified.

The observer in `scripts/native/HmiOptionalObserver` subscribes to CLR assembly-load events and records already-loaded assemblies. It does not redirect or reject loads, reference Siemens, or invoke engineering operations. Windows `Process.Modules` did not enumerate the managed assemblies and is therefore labelled unverified for that purpose. The CLR observation, not an empty Win32 module list, supports the no-HMI-load conclusion.

Earlier retained attempts are intentionally not passing evidence: `…-a` failed while the nested Windows PowerShell signature module could not load; `…-b` timed out in the sandbox before the first bridge response; `…-ordinary-c` passed `bridge_info` but hit Siemens' relocation-dependent `OpennessLocationProvider` failure. Preliminary `…-control-d` passed the calls with core-location bindings, but its empty Win32 module observation is superseded by the explicit managed evidence in `…-observed-e`.

## Assembly identity diagnostics

`artifacts/hmi-optional-startup-20261008-final-major/report.json` records the actual worker's metadata diagnostic against an unsigned synthetic assembly named `TiaMcp.OptionalStartup.WrongVersionFixture`, version 20.0.0.0, copied under the two optional candidate filenames only inside the test API directory. It has no Siemens identity, signature, implementation or dependencies. Both family responses reported `HmiVersionMismatch`, required major 21, observed major 20, with API availability unavailable.

`artifacts/hmi-optional-startup-20261008-final-identity/report.json` repeats the control with the same clearly non-Siemens fixture built at version 21.0.0.0. Both family responses reported `HmiAssemblyIdentityMismatch`, including expected and observed simple names and public-key tokens. The worker obtains its expected token from the loaded `Siemens.Engineering.Base` public assembly identity, observed as `29bfe5fdf4ba5d3b`; the test report verifies the installed Base original's Authenticode signature and hash. The checks also require neutral culture. A candidate filename and matching major version alone cannot mark an HMI module available.

The CLR observer confirms neither metadata fixture loaded as executable code. These controls qualify the metadata rejection branches; they do not qualify native operation with an incompatible Siemens installation. Earlier `…-wrong-major-f` evidence is superseded by the final runs against the worker containing the identity fix.

## Reproduction

Build `scripts/native/HmiOptionalObserver/HmiOptionalObserver.csproj` and, for the separate metadata test, `scripts/native/HmiOptionalWrongVersion/HmiOptionalWrongVersion.csproj`. Run `scripts/qualify_hmi_optional_startup.py` with explicit `--host`, `--worker`, a new `--output` under workspace artifacts, `--bind-core-at-installed-location`, and `--observer` pointing to the built observer DLL. For the separate wrong-major control add `--wrong-version-fixture` pointing to its built fixture DLL. For the wrong-identity control build a separate fixture output using `-p:FixtureVersion=21.0.0.0`, then add `--wrong-identity-fixture`. These two fixture options are mutually exclusive. The runner never changes the supplied executable or its original configuration.

The eight Python evidence-validator tests run through `scripts/Test.ps1`; they do not replace the native host/worker evidence. The probe requires a detached session with no owned TIA process or project, and any abnormal host shutdown prevents an overall pass. The engineering rule suite also checks independent wrong name, token, version and culture cases. A fresh machine with no WinCC installation, actual incompatible signed Siemens modules, and remote-host repetition remain separate acceptance scenarios.
