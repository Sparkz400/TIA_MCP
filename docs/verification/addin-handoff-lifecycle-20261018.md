# Internal Add-In handoff lifecycle — 18 October 2026

Baseline: `37f3c79f134ae3fee007dfb359d97e76907c43c9`. This implements the portable challenge/receipt component of AI-03. It does not install a listener, expose a new MCP tool or establish a production enrollment authority.

## Implemented boundary

The internal coordinator accepts authority callbacks only from trusted application code, not JSON requests. The eventual receiver must supply an OS-verified peer and an independently established producer/enrollment authority. This workstation has neither a real producer nor a verified enrollment route. All exercised authorities are explicitly synthetic, and every returned challenge/status keeps producer authentication, live-selection verification and native qualification false.

The coordinator binds the exact selection bytes, saved review, peer process instance, worker instance, session generation, project host/path, snapshot and declared package/configuration hashes to an authority-supplied binding. A retained evidence hash identifies that authority's enrollment context; the hash itself is not proof of native authenticity. Verification must be side-effect-free, honor cancellation and return the same binding only while the original owner remains current.

Request IDs are reserved by durable directories before challenges are returned. A challenge is 256 random bits, lives for thirty monotonic seconds, stays only in memory and is bound to the receiver instance and peer. A matching peer/token consumes it before reading retained inputs or awaiting authority again; restoring a damaged input cannot revive the token. Wrong peers or wrong tokens cannot consume another peer's challenge. Owner changes, expiry, cancellation and restart prevent completion. There is one store owner, at most eight pending challenges, sixty-four retained requests, eighty MiB of handoff storage and 1,024 filesystem entries. Authority awaits are bounded to fifteen seconds. Network connection/frame limits belong to the still-unimplemented transport.

The existing detached-selection validator and artifact publisher are reused through an internal byte-entry method. Completion writes the consumption marker, rechecks authority, retains the exact selection, rechecks authority again, and flushes the receipt plus its completion hash before acknowledgment. Receipt lookup validates original bytes, the saved review, the selection record and the plan/consumption/receipt hash chain. Lost replies and restart only reopen evidence. There is no native operation, selection reacquisition, automatic receipt adoption, request replay or journal cleanup. Reaching a retention bound refuses further requests; retention management is not delivered here.

## Verification

Actual file I/O is used; peer metadata comes from the test process, not an authenticated transport. Restart is tested by disposing and reopening coordinator objects, and lost acknowledgment by reopening already committed evidence without repeating completion. Actual Host crashes, pipe disconnects and power loss are not exercised by these component tests. The raw statuses retain the explicit synthetic authority flag.
