# Controlled Git paths — 23 October 2026

The combined offline aggregate stopped in the VCI workflow after Git could not
write an object under its long Windows fixture path. The original frozen run
remains failed: 1,662 Python tests (one skip), 25 Explorer model/client checks and
eight managed suites had passed. No later suite or full package pass is inferred.
Its source snapshot is `96d20efc6ba443df902891bea1625197`; its result is retained at
`artifacts/deployment-build/96d20efc6ba443df902891bea1625197/artifacts/combined-20261023/aggregate-01/result.json`.

The production Git process now supplies `core.longpaths=true` on Windows for
each controlled command. This setting is not written to repository, user or
system configuration. Git for Windows documents this option for its C-based
commands, with limitations for other programs and scripted commands:
[vendor guidance](https://gitforwindows.org/git-cannot-create-a-file-or-directory-with-a-long-path.html).

Separate probes exposed two startup boundaries. Windows cannot start the process
with an overlong current directory, and Git checks repository metadata before
long-file handling is available. The adapter now refuses a Windows control/cwd
of 260 or more UTF-16 characters, and a repository whose `.git/objects` startup
path reaches 260. These checks run before repository initialization dispatch or
directory creation. They do not prohibit longer contained files, blobs or export
paths. Unsupported roots return `GitWorkingDirectoryTooLong`.

Failed implicit discovery could also select an enclosing repository. Every
controlled command now receives literal `--git-dir=.git --work-tree=.` relative
to its validated cwd. Missing child metadata therefore fails instead of reading
the outer HEAD. This explicit relative selection also avoids Git's separate
absolute `GIT_DIR` size bound; see the
[Git setup implementation](https://raw.githubusercontent.com/git-for-windows/git/main/setup.c).
