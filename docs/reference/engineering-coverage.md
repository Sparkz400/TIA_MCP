# Engineering coverage expansion

For the latest safety fingerprint and saved-project preservation evidence, see [selected engineering-gap qualification](../verification/engineering-gap-qualification.md). The historical failed/blocked attempts below remain part of the evidence record.

This increment adds reusable inspection and editing operations. A callable route, a pure regression test and a native fixture result are separate claims. The feature catalog keeps new routes **partial** and **unverified** until an exact native run has recorded its target, compile/readback outcome and recovery evidence. Existing evidence continues to qualify only its original fixture profile.

Payloads and the prepare/apply/recovery protocol are documented in [engineering workflows](../guides/engineering-workflows.md). Exact scope and namespace selection are documented in [object identities](object-model.md).

## Graphical preservation contract

The prepared artifact starts from the current native block export. Operations modify only the selected nodes or component names. Network comments, interfaces, peer networks and unsupported native payloads remain in that tree.

`graphical_network_patch` validates the complete candidate network before replacing the original tree. UId definitions must be unique, and known connectors must point to a compatible existing Access, Part or Call. Node removal that leaves a connector unresolved is rejected. A failed patch leaves its input document unchanged. Software-object envelopes hidden inside network fragments are rejected.

`graphical_network_insert` accepts a complete native `SW.Blocks.CompileUnit` after an existing same-language network. Object IDs must be explicit and unused across the exported document. The helper does not guess or renumber object IDs or rewrite unknown references. Graphical UIds remain network-local.

Common XML serializers emit `ns0:Access` and other prefixed FlgNet nodes. A native scratch import demonstrated that Siemens can reject those fragments despite XML namespace equivalence. Incoming fragments now use the native default FlgNet namespace. Extension namespaces are retained; a QName payload value depending on a removable native alias is rejected rather than silently rebound. Existing native content is not rewritten to normalize fragments.

The first retry of that import still launched the older default Debug worker even though its host was a Release build. Its repeated failure therefore did not exercise the new normalization code. The [engineering-layer harness](../../scripts/validate_engineering_layers.py) now passes an explicit Release `--worker` path and records SHA-256 hashes for both host and worker. Qualification evidence must identify the actual worker binary, not infer it from the host configuration.

After import and compilation, the worker exports the block again and compares it to the prepared native document. The comparison excludes top-level `DocumentInfo` export provenance and serialization details such as indentation, attribute order and element namespace-prefix spelling. It retains object IDs, interfaces, instruction/wire attributes, comments, meaningful text whitespace, `xml:space` and QName-value namespace bindings. A difference produces `NativePreservationMismatch` and a recovery-required outcome; the post-export artifact is retained for inspection.

This comparison is deliberately strict. Siemens may normalize inserted native objects or assign IDs during import. Such differences are not automatically approved, even when compilation succeeds. Inspect the evidence and recover the checkpoint before preparing a different change. Import/compile success alone does not satisfy preservation or prove runtime behavior.

## Representative regression coverage

Pure C# fixtures cover native Boolean branch wires and opaque comparison, arithmetic, move, edge, latch, timer, counter and block-call payloads. They assert that unrelated interfaces, comments, unknown namespace elements and peer network content survive edits. They also cover atomic rejection of dangling references, duplicate IDs, hidden objects, unsupported index expressions and safety envelopes.

Call fixtures use exported V21 SCL FC and FB multi-instance layouts. Tests distinguish input/output argument syntax, retain instance XML, expose unsupported expressions, and reject a graphical shared-Access rename that would affect another connection. A separate case verifies that isolated rewiring changes only the selected endpoint.

Some native SCL FC exports omit `CallInfo.Name` and put the function symbol in a global `Instance` element. Call inspection exposes those exact components as `calledTargetComponents` with `calledTargetResolution: "symbolicOnly"`; a single simple component also supplies `name`. Multiple components are not collapsed into a guessed short name. Local, indexed or otherwise unsupported target expressions remain unresolved. For an FC, `instanceKind` and `instanceResolution` remain `notApplicable` because this XML element does not imply an FB instance DB relationship.

Readback tests detect loss or alteration of comments, interface declarations, native IDs, extension payloads, significant text spaces and QName bindings. Namespace-prefix normalization has both positive and ambiguity-rejection cases.

The Python conformance suite covers complete native preservation assertions, unit namespace fixture adaptation, catalog-grounded hardware family selection, blocked missing modules, explicit technology profiles, safety comment/signature prerequisites and recovery result handling. These tests do not execute Siemens operations.

## Native evidence

Native fixture results must identify the exact CPU, firmware, TIA version, software scope, instruction or hardware/technology profile and operation. Retain failed attempts and their recovery records alongside successful reruns. Report missing profiles, services or eligibility as blocked. Do not promote one CPU, module, axis family, safety comment or unchanged XML roundtrip into unrestricted support.

Use the dedicated qualification scripts as appropriate: [software-unit routes](../../scripts/qualify_unit_routes.py), [hardware families](../../scripts/qualify_hardware_families.py), [technology families](../../scripts/qualify_technology_families.py) and [offline safety fixtures](../../scripts/smoke_safety_direct.py). The existing [conformance documentation](../guides/conformance-fixtures.md), [hardware/TO history](../verification/hardware-to-verification.md) and [safety history](../verification/safety-verification.md) retain their original evidence boundaries.

`to_create` accepts at most 500 non-null scalar initial parameters and rejects sensitive parameter names during preparation. Since the technology object does not exist yet, preparation cannot prove that those names, values or dependent hardware settings are valid for it. After creation, the worker resolves each native parameter, checks its current type and available write-access metadata, writes it and verifies the readback before compilation. A missing/read-only parameter, conversion failure, dependent validation error or readback mismatch can leave a partial creation; retain the failure and recover the checkpoint before another attempt.
