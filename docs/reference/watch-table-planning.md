# Captured-evidence watch-table planning

Without Siemens software, `diagnostic_watch_plan` now connects a saved diagnostic
case and its exact review to this library through the normal Host. It returns a
bounded summary and a retained `diagnostic-watch-plan.v1` artifact for download.
See [the diagnostic workflow](../guides/trace-diagnostics.md#produce-an-offline-watch-plan)
for explicit external-storage reasons, caller-supplied version metadata and limits.
This offline route generates no native XML or apply admission.

`TiaMcp.Core.WatchTables.WatchTablePlanner.Plan(WatchTablePlanningRequest)` produces deterministic offline table intent. The planner itself is a pure library API. The separate [WT-04 authoring adapter](watch-table-authoring.md) now connects native exact-instance capture, this planner and the preserving XML editor through production review tools and the durable dispatcher. Native mutation profiles require separate qualification; monitoring and force jobs are outside this slice. The planner implements the WT-02 captured-evidence seam from the [watch/force plan](../plans/expansion-plans/watch-and-force-table-engineering.md).

Provide the exact expected and captured source references, selected instance storage reference/member components, and table name. References use the shared [engineering identity contract](../../contracts/engineering-object-reference.v1.schema.json). `EnsureFresh` compares captured selectors/snapshot/content; it does **not** observe current TIA state. All references must identify the same captured project, PLC and snapshot. Other storage requires a separate exact `WatchTableExternalStorage` allowance and reason. This prevents a MotorA request from silently consuming MotorB, while allowing deliberate actual-parameter or cross-equipment comparisons.

For an existing `DiagnosticPlanner` case, supply its `plan` object and `CanonicalJson.Sha256(plan)`. The adapter binds `reviewId` to `Snapshot.ObservationId`, checks exact project/block/instance identity, and verifies resolved XML evidence against the case's source document hashes and supplied storage content hashes. Tag evidence needs the same review and an exact captured node identity. It preserves diagnostic signal IDs, ordering, symbolic components, hypothesis links, reasons, evidence and upstream gaps. The original signal schema's `onlineAddress:null` remains unchanged. `diagnosticSourceRevisionSha256` separately identifies the case's document-list content; the shared snapshot source hash belongs to the caller's captured source manifest and is not redefined as a native revision counter.

Normalized interface, call-graph, instance-DB, selected-network and I/O-map candidates can be combined with a diagnostic case or supplied alone. They carry exact source/storage references, member components, type, role/reason, resolution, storage class and evidence. The evidence must bind `observationId`, `sourceSha256`, and `objectPath` to its source reference. A resolved candidate additionally carries `declaration:{storagePath,memberPath,datatype,contentSha256}` matching its storage reference. `selectedNetwork` needs an explicit captured `networkId`. Interface/call/network sources match the selected source; instance-DB sources match selected storage. These are explicit captured adapters, not a second parser or proof of a newly inferred language dependency. Raw interface/call/network/I/O extraction and native symbol validation remain with their existing providers and later qualification.

Persistent storage classes are `instanceMember`, `globalDbMember`, `plcTag` and `actualParameter`. `temp`, `inOutAlias`, `indirect` and default `unknown` remain unresolved even if an upstream candidate labels itself resolved. Non-scalar types, missing declarations and namespace ambiguity remain in `unresolvedSuggestions`. The module never guesses an FC local address, expands a pointer, resolves an alias by name or computes optimized-DB offsets. The accepted scalar type set is explicit in source; unknown type profiles remain gaps.

Default ordering follows captured input order: diagnostic signals first, then supplied candidates. A reusable template provides ordered slot IDs, roles and datatypes; every slot requires an explicit candidate binding and explanation. Mapping rechecks role/type and capture identity. Unmapped candidates are retained as source gaps. No instance-name string replacement occurs. Duplicate rows are preserved by default. `collapseExact` merges only identical storage/member/type/symbol/address intent and retains every selection reason and original candidate. Conflicting types for the same captured storage/member fail.

Rows have plan-local zero-based ordinals, `displayFormat:Undef`, `modifyIntention:false`, and no modify value or online address. These are conservative proposed defaults, not confirmed native display choices. Original symbolic components are retained without rendering a guessed native expression. A separate `WatchTableAddressObservation` can retain an exact caller-supplied symbolic or absolute observation. Absolute observations require nonoptimized evidence, explicit area/DB/range, supported scalar width and alignment. They are marked `suppliedOfflineObservationNotNativeQualified`; overlap warnings preserve potentially aliased ranges. This API never acquires or verifies a live address.

Host budgets: 10,000 combined candidates, up to 10,000 requested rows, 1,000 external storage allowances, 32 member/symbol components, 64 diagnostic signals, 64 KiB per supplied evidence object, 4 MiB diagnostic case, 16 MiB combined captured inputs, and 16 MiB output before its digest. These are host limits, not Siemens capacities. Larger evidence can hit the byte budget before the row count. Row-budget omissions retain the candidate and reason. Source truncation propagates separately and contributes to `truncated`. Overlap reports cap at 1,000 warnings with their own truncation flag. Changing a limit requires an explicit request; there is no continuation that silently expands a diagnostic case.

Output follows [watch-table-plan.v1](../../contracts/watch-table-plan.v1.schema.json). `planSha256` hashes the canonical output with that property omitted; object keys are ordinal-sorted and array order preserved. Callers can export the returned JSON using their existing artifact layer. The planner performs no filesystem writes and mutates neither its inputs nor returned evidence aliases. All output keeps `nativeExecutable:false`, `nativeDocumentGenerated:false`, `qualification:offlinePlanningOnly`, and the explicit pending native gates.

Validation uses [the independent authored oracle](../../fixtures/watch-tables/planner/expected-motor.json), [dedicated managed checks](../../tests/TiaMcp.WatchTables.Tests/Program.cs), and a sample produced by the existing DiagnosticPlanner tests. It covers exact instance boundaries, stale/mixed evidence, transient storage, all five normalized source adapters, templates, duplicates/type conflicts, bounded omissions, supplied address mismatches/overlaps, one-thousand-row planning and immutable explanations. The corpus and hashes are recorded in `artifacts/expansion-implementation-20261015/watch/`. Synthetic passes do not qualify native tables, live observability, grammar, persistence or recovery.

Genuine native captures back the [preserving document and production watch workflow](watch-table-workflow.md). Its first qualified scoped mutation edits an existing Bool literal in a worker-owned scratch project. WT-04 now implements planner-backed row materialization and reviewed creation/maintenance, while the new native profiles remain disabled pending independent verification. Broader table/rule profiles and the remaining WT-01/03–10 acceptance criteria stay open. Existing accepted general VM evidence is not scheduled for repetition.
