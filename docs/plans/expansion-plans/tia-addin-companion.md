# TIA Add-In companion: selection, execution ownership and delivery

Baseline: `ec71c96b13b52491e2d6638e2da72f9c8e67b869`, 18 October 2026. Covers X04 / AC-22 in the [full roadmap](api-coverage-and-roadmap.md). This plan preserves the complete companion requirement; the portable selection review below is its first implemented boundary, not completion of X04.

## Outcome and current scope

In TIA, a user selects exact engineering objects, chooses the companion command and receives a review in the existing Host/Explorer workflow. Proposed engineering changes use the existing preparation, approval, operation journal and native worker. The companion must not become an independent writer. Reopening a prior selection or operation receipt must never repeat acquisition or execution.

There is no Siemens installation, SDK, publisher, TIA UI or qualified companion on this workstation. `addin_selection_review` and `addin_selection_page` implement review of **supplied detached selections** against a saved project review. They preserve ordered references and original bytes across Host restart, with producer authentication, live selection and native execution explicitly false. No native DLL, executable launcher, package manifest or authenticated IPC channel is delivered by these tools. [Portable workflow](../../reference/addin-selections.md).

## Boundaries and next step

The portable review accepts a declared selection time as historical metadata. It does not infer live freshness from wall time or an unexpired snapshot. Declared binary/configuration hashes do not authenticate a producer. Repeated byte-identical input gives the same immutable review; different bytes are different observations, not an authorized replay or an operation retry. Multiple records may declare the same sender selection ID because that untrusted ID is not an execution key.

The current `src/TiaMcp.Host/SessionRelay.cs` validates a configured Windows SID/channel, uses current-user-only pipes and starts an owned Host process. It transports byte streams and does not interpret requests. It contains no Add-In producer authentication, native selection challenge or binding to an existing TIA process/worker session. Reusing it unchanged would not satisfy AI-03; a new Host also must not become a second owner of an existing engineering operation. This is a source inspection, not a new relay execution test.

The next Add-In work is AI-03's authenticated ownership/transport contract. The separate [X05](multiuser-project-server.md)/[X09](teamcenter-gateway.md) collaboration route plans and MU-02/TC-02 supplied reviews are delivered; their native implementation packages remain open. AI-02/05/06 native source can advance only where exact signatures and schemas are established; unresolved vendor examples must remain explicit. Full X04 acceptance requires every package above, not just the two portable tools.

## AI-03 owner preflight — 18 October 2026

Source inspection at `5deddf7ab12aa67e857ed3c95d0ea50293065e8c` establishes these integration constraints. This section is a design decision and test queue, not an implemented or authenticated transport.

| Existing boundary | Required handoff behavior |
| --- | --- |
| [Host registration](../../../src/TiaMcp.Host/Program.cs) creates one bridge and registers its guarded `IBridgeClient` dispatcher. | Run the receiver in that existing Host. Dispatch through its existing service and ownership guards; neither discovery nor a companion request creates another engineering Host or bridge. Missing owner means unavailable, not automatic attach/start. |
| [BridgeClient](../../../src/TiaMcp.Core/BridgeClient.cs) launches a worker, serializes calls and makes a transport fault terminal. The original preflight found no connected-peer process check. | The [bridge peer increment](../../verification/bridge-peer-20261018.md) now retains the launched process handle and compares Windows' connected-client PID before the first and subsequent requests, checking the original process is still alive. An actual same-user child running the same binary is refused before any request bytes. This authenticates the local pipe process within the tested scope; it does not authenticate the loaded Add-In, package or native selection. |
| [Native status](../../../src/TiaMcp.Openness.V21/OpennessSession.cs) originally exposed only `processId` and `ownsPortalProcess`. The [owner-context increment](../../verification/addin-owner-20261018.md) adds retained OS identity and a private read-only `addin_owner_context` route; normal status is unchanged. [Project models](../../../src/TiaMcp.Openness.V21/OpennessSession.ProjectModel.cs) rotate `sessionGeneration` on attach/start/detach. | The receiver must bind Host, worker, native process, current generation, exact project and snapshot. The new route supplies OS observations and a native PID comparison, not native attestation. It accepts no caller-selected identity and never starts or attaches. Native acquisition/clock/lifetime interoperability still needs qualification; ownership of the connection does not require ownership of the user's TIA process. |
| [AddInSelectionStore](../../../src/TiaMcp.Core/AddInSelectionStore.cs) validates detached input against a saved review and retains immutable artifacts. | Reuse detached selection validation and retention after transport admission. Its saved-review match remains historical evidence; it cannot manufacture the live owner, loaded companion identity or mutation permission. |

The receiver must distinguish four claims: the OS identity of the connected process/user; possession of a fresh request challenge; verification of the loaded companion and its pinned package/configuration; and revalidation of the selected native objects by the existing worker. A same-user pipe, executable hash or returned nonce alone does not prove all four. In particular, a TIA executable hash does not identify an Add-In DLL loaded inside it. Enrollment and the native producer's trusted package/lifetime route remain explicit AI-02/06 gates; accepting a self-declared hash or an ordinary uploaded secret cannot bypass them.

The planned exchange is one bounded selection request, not arbitrary MCP forwarding: discover the existing owner, verify the peer and enrolled producer, issue a fresh challenge bound to the full owner tuple and request digest, consume it once under that owner, then persist the detached selection and its handoff receipt before acknowledging. Expiry, cancellation, owner change and Host restart invalidate pending challenges. Repeated receipt lookup is read-only; a lost reply must never reacquire selection or dispatch native work. A changed payload under the same request identity refuses. Publication interruption must remain inspectable and must not create a second receipt by repeating native acquisition.

Portable acceptance must cover an impostor process under the same user, wrong owner/worker generation, reused or expired challenge, changed request bytes, malformed/oversized/slow frames, concurrent consumption, peer/owner exit, receipt publication failure and lost acknowledgment/restart. Tests must assert that refusal makes no native call. The complete receiver must also enforce finite connection, pending-request, frame, deadline and retention limits. Exact production protocol fields and bounds belong with that implementation and its schema; this preflight does not declare a usable wire format. Genuine loaded-package identity, TIA process binding, callback lifetime and interactive selection still need native execution.

The subsequent bounded existing-Host receiver integrates the internal one-use challenge/receipt lifecycle. Its production authority remains unavailable: the eventual owner/enrollment adapter must obtain owner context through the verified bridge, never request fields. The bridge and transport corrections do not complete AI-03; trusted producer enrollment, native owner qualification and the native client remain explicit work.

The owner-context prerequisite has production source and portable OS/.NET Framework checks. The complete native worker is not SDK-built here. Neither the internal context route nor its `available` state constitutes an admitted handoff; receiver implementation and its remaining gates are described below.

The [owner-discovery regression](../../verification/addin-owner-discovery-20261018.md) closes a bridge-layer startup side effect: `addin_owner_context` on an unused Host refuses before worker launch, while later explicit work remains usable. The trusted loaded-producer enrollment route is still unresolved in the inspected sources. Keep that authority distinct from OS peer verification when implementing and testing the remaining bounded receiver and challenge/receipt flow. No production admission may be enabled by a synthetic test authority.

The [internal handoff lifecycle](../../verification/addin-handoff-lifecycle-20261018.md) provides durable request reservation, monotonic one-use challenges, owner rechecks, detached selection retention and receipt lookup without replay. The subsequent [bounded receiver](../../verification/addin-receiver-20261018.md) integrates it into the existing Host under explicit `--addin-handoff`, with actual pipe, process crash, peer exit, capacity/deadline and production-refusal checks. Trusted producer enrollment, the production owner adapter and native client/selection qualification remain required before production admission. No synthetic provider is registered by production Host. Full AI-03 and the full 44-workstream scope remain open.
