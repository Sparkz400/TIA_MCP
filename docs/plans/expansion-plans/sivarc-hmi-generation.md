## 3. Architecture and proposed contracts

The following names and schemas are **proposals**, not installed tools or supported operations.

Keep the portable .NET Host/Core independent of Siemens assemblies. Put typed native SiVArc calls in an optional V21 adapter following the existing HMI assembly-loading boundary. Decide between an optional module within the current worker and an additional isolated worker only after SV-01 proves loading/license/lifetime behavior; do not create a second process architecture preemptively. Exchange plain DTOs, never Siemens objects.

| Proposed surface | Inputs and output contract |
| --- | --- |
| `sivarc_inspect` | Exact saved/native project target, family and bounded section selection. Return capabilities, definitions/rules/library references/selections with completeness, errors and original native evidence. Missing product is a structured unavailable result. |
| `sivarc_expression_review` | Exact compiled PLC block, HMI target, library item and expression. Retain per-instance result/call-path evidence with the input revision. Native resolution is separate from offline file review. |
| `sivarc_generation_preview` | Existing component-review ID plus exact rule/template/library versions, PLC/HMI identities, languages, acquisition configuration, prior generation manifest and requested options. Return conflicts, affected resources, unresolved coverage and proposed operation plan. Without a supported dry-run, label predicted effects as expectations; use an admitted scratch copy for actual generated comparison. |
| Existing change lifecycle, proposed kinds `sivarc_rules_edit`, `sivarc_layout_import`, `sivarc_definitions_upgrade`, `sivarc_generate` | Separate prepared operations with exact before fingerprints, dependencies, checkpoint strategy and qualified profile. Reuse existing prepare/apply/status/restore admission. Introduce each kind only with handler, schema, catalog, documentation and applicable tests together. |
| Existing artifact/page/job surfaces | Immutable inspect/preview/result artifacts, bounded pages and durable operation status. Do not duplicate generic downloads, pagination or job polling. |

Proposed `sivarc-generation-plan.v1` includes: schema version; saved review identity; native project/session identity and revision; exact HMI/PLC paths; product/build/API hashes; library type/version GUIDs or master-copy source hash; rule/definition/layout/language hashes; explicit options and resolved device-column identities; prior generation ID and previous/current PLC sets; independent expected outputs and binding/member mappings; all affected resources/consumers; coverage gaps; required gates and checkpoint references. Do not permit arbitrary local paths, scripts or assembly/type names in public input.

Proposed `sivarc-generation-record.v1` binds that plan hash to job/revision, actual before/after evidence, original feedback, generation status, compile/reopen/recovery outcomes and preservation comparisons. Record `generated`, `manual`, `mixed` or `unknown` ownership with its evidence and object/property scope. A name prefix or user claim never proves ownership. A generated object that a user edited becomes a conflict until an explicit preserving strategy is verified.

Use the existing snapshot/session-wrapped HMI identity, canonical object path and exact library identity. Names remain display data. Any change to project content, target, rule/template source, selected language, prior generation set or library closure invalidates a prepared plan. Resolve identities again immediately before apply. Rename mappings must be explicit and one-to-one where required; unmatched additions/removals remain distinct.

Starting bounds are design choices, not Siemens limits: reuse C01's 4 MiB request, 256 proposed outputs, 1,024 mappings, 32 files, 16 MiB/file and 64 MiB aggregate. Retained report maximum 16 MiB, pages at most 200 rows/128 KiB, store capacity 512 MiB. SV-02 may introduce streaming artifacts for larger qualified profiles, with explicit maximum bytes/rows/depth and continuation. Never truncate a required preservation inventory and still permit apply. Preserve raw result bytes within declared bounds; overflow during a native call is an incomplete/unknown outcome requiring reconciliation, not evidence of native cancellation.

For regeneration, use an evidence-based three-way comparison: last accepted output, current project content and expected new output. Byte equality is sufficient only for opaque unchanged files; semantic comparison needs a supported exact format/profile. Preserve unsupported subtrees. Conflicting edits, missing baseline, incomplete consumers or unknown source content block native write admission. An offline review can still report these gaps usefully.

Jobs reserve the exact project plus libraries that may be written; inventory shared screen/type consumers across the project. Source libraries stay read-only unless explicitly included. Archive before modifying; retain source artifacts and restore into a fresh destination. A timeout/disconnect records unknown outcome and holds admission until inspection/recovery settles every resource. A client cancellation must not be reported as successful native cancellation. Do not kill unrelated TIA instances, retry a generation blindly or manufacture a clean rollback receipt.

## 5. Concrete initial generation and interface-change example

This is an authored acceptance design, not a claim that this fixture exists or has run. Start with exact `MotorControl` library version 1.2.0, two explicitly identified instances, a compatible Unified target, and a matching faceplate/screen template version. Use named members `Start : Bool`, `SpeedSetpoint : Real`, `ActualSpeed : Real` and `Fault : Bool`; reviewers author the expected mapping independently of generator output.

1. Capture source/library closure, both instance call paths, destination identities, connections, project languages and whole-project HMI content. Include a manually authored overview screen and an unrelated instance of a shared screen type as preservation sentinels.
2. Review exact library/component integration and all prerequisites. Pin templates and rule tables; explicitly select member acquisition settings and `en-US`/`de-DE` resources. Author expected tags/bindings, two faceplates, navigation destinations and fault text resources. Resolve native expressions against both instances. Incomplete call/consumer evidence blocks apply.
3. Preview intended create/update/delete effects and full affected scope. Generate on an admitted owned fixture with recoverable checkpoint; compare exact actual content to independent expectations, compile PLC/HMI and inspect every sentinel. Retain native feedback even if its success flag is true. Save, close and freshly reopen, then separately retrieve the original archive into a fresh location and prove recovery.
4. Update to version 1.3.0: explicitly map `SpeedSetpoint` to `SpeedCommand`; add `Running : Bool`; remove a deliberately obsolete test member. A rename is not guessed from similar spelling. Independently recompute all bindings, expressions, text references and consumers. A manual edit to one generated label must appear as a conflict, not be overwritten silently.
5. Resolve that conflict by moving the intended label change into the supported template/property source, or choosing another proven preserving strategy. Protect manually authored navigation, unrelated HMI content and every shared-type instance. Generate with explicit recorded scope/options, compare expected member/type changes and all preserved content, repeat compile/persistence/recovery and applicable visual/runtime checks. A second identical regeneration tests stability without treating harmless native serialization churn as a semantic change.

The existing portable C01 review can already examine supplied component/interface/output files for portions of steps 1 and 4. It cannot perform steps 2–5 natively or certify complete preservation.
