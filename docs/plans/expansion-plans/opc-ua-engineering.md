# OPC UA engineering expansion plan

**Release scope update — 15 October 2026:** The user requires every feasible capability before 1.0. Read the [current release ledger](../release-obligations-20261015.md) before scheduling work. Older wording that permits optional expansions, selected-only release scope or a reduced 1.0 is superseded. Missing prerequisites and unresolved feasibility remain release blockers; recorded passed/failed evidence and native/UI scheduling boundaries remain intact.

Planning baseline: 14 October 2026, Europe/Berlin. Status: proposed implementation and qualification plan; no OPC UA native acceptance executed. All new tool, change-kind, schema, profile and module names below are proposals. This document does not authorize implementation or a native run.

The intended outcome is a recoverable, versioned machine-information-model workflow: discover the exact eligible PLC, import namespace dependencies and a mapped interface, explain externally visible identities and access, apply a reviewed change, compile and inspect the result, export a client handoff, verify fresh reopen, and demonstrate recovery. Expansion covers every useful public route found below, including SIMATIC interfaces, generation, namespace access control, legacy users, certificate configuration and eligible HMI settings. Offline configuration and physical runtime remain separate products of the architecture.

### 2.3 Documented differences and format constraints

Installed accessors are decisive for what can be compiled against this installation: reference and SIMATIC `Name` are writable; custom `ServerInterface.Name` is not. D2/D3's older property tables call both names read-only. D4 explicitly announces reference rename/generation. Keep the SIMATIC discrepancy in the API manifest and qualify it, rather than deleting the installed route or treating it as a proven target capability. `Comment` is a read-only reference to a multilingual text object; localized edits use its public item API, not property replacement. Creation/last-modified timestamps are observations, never user-authored values.

The exact I2 policy symbols are `None` (zero), `OpcUaSecurityPoliciesNone`, `OpcUaSecurityPolicies128RSAS`, `...128RSASE`, `...256S`, `...256SE`, `...256SHAS`, `...256SHASE`, `...256RSAOAEPS`, `...256RSAOAEPSE`, `...256RSAPSSS`, `...256RSAPSSSE`. D5 calls the zero value `NoneSelected`; retain the installed symbol and the documented semantic distinction. The flags encode both policy and signing/encryption mode; do not model security mode as an unrelated freely combinable value. Preserve existing configuration in read-only discovery. New secure fixtures use an agreed supported signing/encryption profile; weak existing profiles are reported, not silently rewritten.

Keep three formats separate: (a) native PLC SimaticML exports for declaration evidence; (b) UA interface/NodeSet documents and any supported Siemens mapping extensions; (c) bridge JSON model/impact manifests. Siemens documents NodeSet2 companion inputs and SiOME can validate against `UANodeSet.xsd` ([SiOME schema-validation setting](https://docs.tia.siemens.cloud/r/en-us/v3.2.0/siome-manual/general/default-settings/settings-in-tab-general)). No particular NodeSet schema revision or Siemens mapping extension grammar was established by the local XSD inventory. A standard XSD pass cannot prove a TIA import, supported CORE version or correct PLC mapping.

UA-01 must pin the actual accepted root namespaces, schema/version, CORE/DI/companion model versions, `RequiredModel` closure and extension grammar from official sources plus independent exported fixtures. Do not invent a `SW.OpcUa_v*.xsd`, assume that general SimaticML V18-V21 compatibility applies to UA, or fetch `schemaLocation`/namespace URIs during parsing. XML DTD/entities and network resolvers are disabled. Retain original bytes, unknown nodes/attributes and namespace aliases; unsupported semantic edits fail before mutation. Exact NodeSet bytes and supported mapping patches are separate operations with explicit preservation coverage.

### 3.2 Mapping and identity rules

Persist engineering identity as the existing project/PLC/scope/object reference plus interface category, parent composition, observed name, native type and content fingerprint. For members, add an ordered path of declaration components and explicit array-index tuples, preserving quoted names and namespace/scope qualification. Obtain DB/UDT/tag identity from complete declaration evidence; do not join on short names, display strings, numeric DB address alone or assumed globally unique PLC symbols.

Persist UA identity as `{namespaceUri, identifierType, identifier}`. Keep numeric/string/GUID/opaque IDs distinct. Store original namespace index and URI-table mapping as evidence, but compare by expanded identity; indices can change after import or runtime restart. Do not case-fold URI, NodeId or BrowseName. Compare BrowseName qualified namespace/name, DisplayName locales and Description separately. A changed display label is not necessarily a changed NodeId; a changed namespace URI is an identity change even if local numeric IDs are unchanged.

Mapping states include `resolved`, `constantModelValue`, `unmapped`, `ambiguous`, `declarationMissing`, `typeIncompatible`, `methodSignatureMismatch`, `protected`, `unsupportedExtension`, `stale` and `notInspected`. An intentional information-model object/type/property with no PLC backing is not automatically invalid. Required variable/method bindings cannot pass while unresolved; counts and coverage must remain explicit.

Type validation must cover signedness/width, Boolean, floating precision, string/WSTRING encoding and length, date/time/status representations, enums and aliases, UDT/structure member order, nested structures, scalar versus array rank, dimensions/lower bounds, and whole-array versus element exposure. No silent numeric/string coercion. Preserve PLC lower bounds even where UA dimensions express lengths only. Resolve symbolic bounds only with exact constant evidence. Method execution and output behavior are a later runtime test. TO/system-generated/protected declarations are read/eligibility cases, not permission to alter them.

Drift checks compare the model plus **every transitive referenced declaration/type/namespace/access/certificate assignment**, selected hardware settings and whole sibling-interface inventory at prepare and again under exclusive access at apply. Rename/move/retrieve changes engineering identities and demands re-resolution; semantic content equality does not authorize following a stale path. Preserve both sides of dependency edges and tombstones so removed nodes still produce client impacts. Declaration changes in existing PLC tools must warn/refuse when newly tracked UA mappings become invalid according to that tool's dependency policy; an uninspected UA dependency cannot be reported as absent.

### 4.3 Security and recoverability decisions

Read and preview configured access without claiming effective runtime permissions. Effective-access evaluation must account for node attributes/model role permissions, namespace defaults/restrictions, mapped project role and CPU function rights, enabled user/auth mode and server policy. Unknown inheritance or unexposed node permission details produce `unknown`, not permissive defaults. Do not change anonymous access, project protection, global certificate-store mode, GDS settings or endpoint policy as an incidental import side effect.

Store credential/password/private-key material outside ordinary exports with current-user ACLs and DPAPI CurrentUser protection (or the future agreed OS credential broker). Handles bind purpose, target/store, creator identity, expiry and rotation version; preparation can validate handle metadata without exposing the secret. Convert to SecureString only for the needed native call and minimize plaintext lifetime. Redact logs, previews, exceptions and journals; no passwords in command lines. Reuse credentials already supplied for the same authenticated project/CPU according to the surrounding session policy; otherwise obtain both username/password through the established protected authentication flow identifying that target. No credential collection is needed for this planning task.

Certificate metadata includes SHA-256 fingerprint, subject/issuer, SAN and ApplicationUri, validity, usage, algorithm/key size, store/assignment and private-key-presence flag. Creation uses only template fields actually exposed; do not promise a key-size setter absent from `CertificateTemplate`. V21's documented key-length warnings/errors (D17) must stay visible. If the native template cannot create the agreed compliant certificate, use a supported secure import workflow or report blocked. Rotation is create/import new certificate -> reviewed assignment -> validation -> separately reviewed retirement; never overwrite a shared certificate blindly. Export only formats proven public-only by an independent parser; private-key export is not part of the ordinary artifact tool.

Project archives may contain sensitive configuration; apply restricted retention/access. A restored project does not restore an externally rotated credential, a live GDS store or a downloaded runtime configuration. Journal those resource boundaries; failure recovery promises only verified affected offline resources. Shared global-store mutation remains blocked until its public API, checkpoint ownership and multi-resource recovery are established. Unknown native outcomes fault the session; persist stages before/after native calls, never replay automatically, and reconcile using journals plus a new authorized observation/recovery copy. Do not treat closing a worker as rollback.

## 5. Complete versioned machine-model workflow and runtime handoff

The first useful release candidate is **model delivery and a deliberate breaking update on one fully qualified PLC/custom-interface profile**, with all supporting namespace, mapping, preview, preservation and recovery work. Read-only inventory alone is not the acceptance endpoint.

Fixture (independently authored, names illustrative): two PLCs, two unrelated interfaces, one companion/reference dependency and an instance model. PLC A has `DB_Machine.Axis.Speed : Real`, `Temperatures : Array[1..4] of Real`, a nested status UDT, and a supported `ResetCounter` server-method instance with a fixed signature. PLC B intentionally contains same short declaration names. The model namespace `urn:example:machine:1` uses explicit stable string IDs if that profile is accepted. Model metadata carries semantic version and publication date independently of bridge schema version. The exact XML, data type mapping and method scaffold must be generated/verified from supported public formats in UA-02, not assumed valid from this prose.

1. **v1.0.0 baseline:** validate dependency versions/ordering, exact declarations, access policy and consumer manifest; prepare/import under one checkpoint, compile, export/read back the exact model, save/fresh reopen, and retain all baseline artifacts. Preserve source files and unrelated PLC/interface/access/certificate content.
2. **v1.1.0 additive revision:** add one temperature/status node without changing existing expanded NodeIds, BrowseNames, types or access. Compare with v1.0 and test that existing declared consumers still resolve. Classify changes in closed enumerations or array shape conservatively; an addition is not universally safe for every consumer.
3. **v2.0.0 intentionally breaking revision:** replace `nsu=urn:example:machine:1;s=Machine.Speed` (Float mapped to `Axis.Speed`) with `nsu=urn:example:machine:2;s=Machine.Axis.Speed` (Double mapped to an explicitly changed LReal declaration), and change one method argument type/order in a separately identified case. Do not create a compatibility alias implicitly. If moving namespaces requires replacement, use `opcua_model_replace`; changes to PLC declarations use the existing prepared PLC route and are checkpointed in a manifest-bound ordered workflow, not an invented atomic cross-tool transaction.
4. **External-client impact:** an authored consumer manifest names `Historian-A` (exact old speed ID/Float), `Dashboard-B` (qualified BrowsePath), and `MES-C` (method ID/signature). Report each old/new identity, removal/addition, type/rank/access/signature changes, evidence path and required migration. Retain consumers of removed nodes; list unregistered clients as unknown. A model scan cannot discover all external applications or prove their source code compatible.
5. **Review/apply/deliver:** preview includes API prerequisites, mapping/declaration effects, URI/index/NodeId differences, security changes, regenerated objects, impacted clients and checkpoint scope. After reviewed apply, require full native diagnostics, exact independent readback, saved fresh reopen and client-contract validation against exported artifacts. Compile success alone is insufficient.
6. **Recover:** use two explicitly separate recovery cases. For initial installation, restore the checkpoint taken before the first namespace/interface mutation and prove the original pre-install project and peers match (the new model must be absent). For the v2 update, freeze v1.1 first, take the checkpoint before the first affected PLC-declaration or model mutation, and restore that checkpoint into a new owned directory/process. Verify complete v1.1 model/declaration/peer equality, reopen again, and prove the old identities/consumer contracts match. Preserve the failed/breaking attempt and recovery lineage. Do not describe offline restore as rolling back a PLC or external clients.

Runtime handoff artifact (proposed schema v1) carries exact project/PLC identity and source fingerprint, profile, model semantic version/hash, namespace URI table, expanded NodeIds, mapping/type/method/access expectations, configured endpoint/ApplicationUri and public certificate fingerprints, evidence IDs and freshness limits. It contains **no session, credentials, private keys or permission to connect**. Configured endpoint is an offline expectation, not evidence of a reachable or correctly deployed CPU.

The future physical adapter described in `../expansion-prompts/16-physical-plc-runtime.md` owns explicit endpoint selection, verified CPU/application identity, authentication/trust, namespace-index resolution, browsing, subscriptions/read quality/timestamps, reconnect/gaps, buffering and any later separately authorized calls/writes/GDS/commissioning. It must compare observed namespace/type/program/model evidence to the handoff and mark mismatches/stale bindings. Offline equality is insufficient to identify a physical CPU. Engineering consumes protocol evidence by exact handoff/model/binary ID; it does not embed competing UA connection code or translate simulator tickets into physical authority.

## 7. Qualification and independent acceptance

Every run manifest binds canonical source snapshot SHA-256 (no Git head is available), host/worker/optional-assembly hashes, TIA version/update/API hashes, fixture original/archive hashes, CPU order number/firmware/profile/license observations, model/schema/dependency/consumer hashes, harness and independent auditor hashes, operation/preview/journal IDs, exact process ownership and UTC timestamps. Protocol runs additionally bind deployed program/model revision, endpoint/CPU/certificate identity and adapter binary. Hashes must be checked immediately before and after the run. A stale input or truncated required observation invalidates acceptance.

Use independently authored expectations: golden expanded NodeIds, declaration component paths, UA types/ranks, methods/arguments, role permissions and before/after peer sets. The writer must not generate its own expected result using the same transformation/parser. Parse retained native exports with an independent checker; retain raw bytes and exact declared normalization rules. Do not discard arbitrary IDs, XML order, namespace URIs, comments or unknown attributes to make equality pass. Only independently demonstrated nonsemantic exporter fields may be excluded, narrowly and visibly.
