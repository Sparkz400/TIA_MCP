# Contract freeze policy (draft)

> **Draft, 1 November 2026. Not in force.** A proposal for the maintainer to decide on, for the
> TODO box [Contract freeze](../TODO.md#release-mechanics-and-policy): which tool names,
> input and output schemas and error codes 1.0 freezes, and how they may change afterwards. Every
> choice that is not settled is listed under [open decisions](#open-decisions) with options and a
> recommendation. Until it is accepted, the CHANGELOG rule stands: before 1.0 any release may
> change the tool surface.

## Proposal

### Frozen at 1.0

A frozen element changes only as [the versioning rules](#versioning-rules) allow.

- **Tool names** of every tool a normal Host registers, including the `base` tools. Which tools
  count is decision [Q1](#q1-which-tools-are-frozen).
- **Inputs:** parameter names, JSON types, whether a parameter is required, documented enum values
  and documented defaults. Inside a free-form JSON parameter, the fields its description or
  reference page documents count as frozen ([Q4](#q4-change-kind-payloads-and-free-form-json-inputs)).
- **Change kinds:** each kind name and its documented payload fields.
- **Annotations, in the safe direction:** a tool may become more cautious (`readOnlyHint` true to
  false is the unsafe direction and needs a major release; adding `destructiveHint` true is
  allowed in a minor release).
- **Declared output schemas** of the 87 tools and any added later: no field removed or renamed,
  no meaning changed ([Q2](#q2-outputs-without-a-declared-schema)).
- **The error envelope** and `isError`, and the error codes the registry marks stable
  ([Q3](#q3-which-error-codes-are-frozen)).
- **Prompt names and arguments, resource URI templates** (`tia://feature-catalog`,
  `tia://feature-catalog/{featureId}`, `tia://artifacts/{+path}`, `tia://project-reviews/{reviewId}`)
  and the completion targets.
- **The `feature_catalog` document shape** (`schemaVersion` 1), not its content.
- **Host options** that are not qualification-only, and the launcher parameters that set them
  ([Q12](#q12-host-options)).
- **Safety semantics:** ownership gates (owned PLCSIM instances, owned scratch projects), required
  acknowledgement flags, the no-replay rule for uncertain outcomes and checkpoint-before-change
  never weaken in a minor or patch release.

### Experimental at 1.0

Usable, documented, and allowed to change in a minor release with a CHANGELOG entry.

- `qualification_*` tools and every qualification-only option (`--component-qualification`,
  `--watch-qualification`, `--runtime-qualification`, `--testsuite-scope-probe`,
  `--testsuite-qualification`, `--translation-qualification`, `--hmi-text-list-qualification`)
  and the build-gated `--safety-fparameter-discovery`. They stay out of the normal advertisement.
- `--toolsets` group names and membership ([Q5](#q5-tool-groups)); `all` as the default
  and the always-advertised `base` tools are stable.
- The catalog version's place under `capabilities.experimental`, the MCP extension namespace.
- The Explorer's MCP Apps view (`ui://tia-project-explorer/view.html`).
- Tools the catalog marks experimental at release ([Q1](#q1-which-tools-are-frozen)).

### Not part of the contract

- Catalog content: statuses, limitations, evidence IDs and support classes. These are data; a
  feature moving from `limited` to `shipped` or back is a CHANGELOG entry, not a version break.
- Tool titles, descriptions and server instructions as text (the fields a description documents
  are covered above), log record text, progress cadence, refusal `message` text.
- The bridge protocol between Host and workers, worker operation names and the artifact store's
  internal layout. Host and workers ship together; a mismatch is refused (`ProtocolMismatch`).
- What Siemens decides: a TIA update that removes an Openness route turns a tool into a typed
  refusal and may lower its support class; the tool name and envelope stay.

### Versioning rules

The product version follows [SemVer](https://semver.org/) over the frozen surface.

| Release | May contain | Examples |
| --- | --- | --- |
| **Major** | Removing or renaming a frozen tool, change kind, prompt, resource template, stable error code or Host option; a new required input; a changed type, default or meaning of a frozen field; removing a field from a declared output schema; changing the error envelope; an annotation flip in the unsafe direction; dropping an MCP protocol revision a released version negotiated ([Q11](#q11-mcp-protocol-revisions)) | `sim_area_write` renamed; `change_prepare` needs a new required argument |
| **Minor** | New tools, change kinds, optional inputs, output fields, enum values, stable error codes, prompts, resources or Host options; new output schemas for tools that had none; deprecations; experimental changes; a safety or security tightening under [Q9](#q9-safety-and-security-tightening) | A new `sim_record` tool; `sim_event` gains `profileEvent` |
| **Patch** | Fixes that keep every frozen element; documentation; a safety or security tightening under Q9 | A refusal that now names the right code |

Clients must tolerate unknown output fields and unknown enum values, as the contract rule already
says; an unknown enum value is never success.

### Deprecation

1. **Mark** the element: a catalog field `deprecation: {since, replacement, removalNotBefore}`
   (new, shown in the tool reference), the description prefixed `Deprecated since X.Y; use Z.`,
   and a `Deprecated` entry in the CHANGELOG.
2. **Warn** at use: one `notifications/message` at Warning level per session for a deprecated
   tool, and a stderr line for a deprecated Host option.
3. **Keep it working** until the next major release and for at least the window of
   [Q6](#q6-deprecation-window). A deprecated Host option may be accepted with no effect, as
   `--enable-library-integrate-apply` is today.
4. **Remove** it only in a major release, under `Removed` in the CHANGELOG with its replacement.

A stable error code is not renamed within a major version. A refusal that needs a finer code keeps
the old one and adds the detail in another field.

### Product and catalog versions

- The **product version** is the only version the freeze is measured against.
- The **catalog version** stays a data version ([Q7](#q7-catalog-version)): it changes with every
  catalog edit, and a content change never forces a product release.
- **Data contract versions** (`*.vN.schema.json`) are independent. A new `vN` beside an accepted
  older one is a minor change; dropping an accepted version is a major change.
- Every release records both versions: the CHANGELOG section names the catalog version, and
  `manifest.json` gains `catalogVersion` (today it records only `productVersion`).

### Persisted state

A 1.x Host reads the journals, checkpoints, admission records, saved reviews, vault and identity
store an earlier 1.x Host wrote, or refuses them with a typed code and a documented way forward;
it never reinterprets them silently, and it never replays an uncertain outcome found in an older
store. The exact promise is [Q10](#q10-persisted-state).

### Enforcement

Proposed, not built:

- **Surface baseline.** A generated `contracts/mcp-surface.v1.json` holding the tool names, input
  schemas, annotations, output schemas, prompts, resource templates, stable error codes and Host
  options, taken from a live Host's `tools/list` and friends. A test diffs the live surface against
  it and fails on any breaking change unless the major version in `Directory.Build.props` moved.
  The baseline is cut on the release candidate.
- **Error registry.** A generated `docs/reference/error-codes.md` (like
  `scripts/tool_reference.py`) listing every code with its tools and its class, stable or detail.
- **Release gate.** `release.yml` runs the surface test for `v1.x` tags next to the existing
  ledger and matrix gate.

## Open decisions

### Q1. Which tools are frozen?

At 1.0 every open matrix cell is closed or dispositioned, but tools whose rows V21 cannot close
(`unavailable_target`) may still be registered.

- (a) Every tool a normal Host registers.
- (b) Every `shipped` or `limited` tool (312 today, both classes rest on verified evidence); the
  rest are marked experimental in the catalog and the tool reference.
- (c) Only `shipped` tools.

**Recommendation: (b).** A name with no qualifying evidence should not be promised; (c) would
leave most of the surface unfrozen, since 183 tools are `limited` by design.

### Q2. Outputs without a declared schema

218 normally advertised tools return structured content with no `outputSchema`.

- (a) Freeze only declared schemas; other outputs are experimental until a schema lands, which
  is a minor change.
- (b) Give every frozen tool a schema before 1.0.
- (c) Freeze the fields the reference pages document, schema or not.

**Recommendation: (a) with (c)'s floor:** a field documented in `docs/reference/` is not removed
in 1.x without deprecation. (b) is a large job, and some contracts cannot be advertised yet
(cross-file references, `prefixItems`).

### Q3. Which error codes are frozen?

- (a) All of them, about 720.
- (b) The envelope plus a registry of stable codes: outcome and recovery codes (`OutcomeUnknown`,
  `RecoveryRequired`, `ReconciliationIncomplete`, ...), gate refusals (`OwnedInstanceRequired`,
  `NativeWorkersDisabled`, ...) and every code a description, reference page or schema names;
  the rest are detail codes that may change in a minor release.
- (c) The envelope only.

**Recommendation: (b).** Clients branch on the outcome and gate codes; freezing all 395
worker-only codes would freeze internals.

### Q4. Change-kind payloads and free-form JSON inputs

- (a) Freeze kind names and the payload fields their documentation names.
- (b) Also publish a JSON Schema per kind and per free-form parameter before 1.0.
- (c) Freeze kind names only.

**Recommendation: (a) for 1.0**, adding per-kind schemas in 1.x minors.

### Q5. Tool groups

- (a) Stable names and membership.
- (b) Stable names; tools may join a group but never move between groups.
- (c) Experimental in 1.x.

**Recommendation: (c)**, with `all` and `base` stable. Client tool limits are still being learned,
so groups may need splitting.

### Q6. Deprecation window

- (a) At least one released minor version before the removing major.
- (b) At least six months.
- (c) Both.

**Recommendation: (a) plus at least 90 days**, which suits a project without LTS.

### Q7. Catalog version

- (a) Independent, as today, recorded in the CHANGELOG and `manifest.json`.
- (b) The catalog moves to `1.0.0` with the product; content changes bump its minor or patch, and
  its major moves only with the product's major (when `schemaVersion` changes).
- (c) The catalog version equals the product version.

**Recommendation: (b).** It keeps catalog edits free of product releases and still tells a
reader which product line a catalog belongs to. (c) would force a release for every evidence
update.

### Q8. Support window

- (a) Keep the current policy: newest release and `main` only.
- (b) Security fixes for the previous minor for a fixed time.
- (c) A 1.0 LTS line.

**Recommendation: (a) for now**, revisited when there are outside users.

### Q9. Safety and security tightening

May a minor or patch release refuse an input a frozen tool used to accept, when that prevents
data loss, an unsafe target action or a security issue?

- (a) Yes, with a typed code and a `Security` or `Changed` CHANGELOG entry.
- (b) Only in a major release.

**Recommendation: (a).** The F-I/O address refusal added to `tag_create` before 1.0 is the
pattern.

### Q10. Persisted state

- (a) Every 1.x Host reads every earlier 1.x store.
- (b) It reads it or refuses with a typed code and migration notes.
- (c) No promise; upgrade instructions say to finish or restore open changes first.

**Recommendation: (b)**, and the release candidate's upgrade, recovery and rollback instructions
([TODO](../TODO.md#release-mechanics-and-policy)) also say to resolve open admissions before an
upgrade.

### Q11. MCP protocol revisions

- (a) 1.0 records the revisions the pinned SDK negotiates; dropping one is a major change.
- (b) No promise; the Host follows the SDK.

**Recommendation: (a).** A client that worked with 1.0 should keep working through 1.x.

### Q12. Host options

- (a) Freeze every option that is not qualification-only.
- (b) Freeze only the options the launcher scripts pass; the direct-launch options
  (`--addin-handoff`, `--git-remote`, `--library-limits-file`, ...) stay experimental.

**Recommendation: (a).** Users put these options in client configurations.

### Q13. A naming pass before the freeze

- (a) Freeze the names as they are.
- (b) One review of tool and change-kind names before the release candidate, with renames
  shipped as deprecations.

**Recommendation: (a)**, unless that review finds a concrete clash.

- Add the policy to [releasing](../guides/releasing.md), [SECURITY.md](../../SECURITY.md) and the
  [MCP surface](../reference/mcp-surface.md) page, and the `deprecation` field to the catalog
  schema.
- Build the surface baseline, the error registry and the release gate, then tick the TODO box.
